# Совместимость репликации

В приложении **0.4.1** используется `replication_protocol_version = 3`.
Это константа формата обмена, отдельная от версии приложения, схемы SQLite
и версии maintenance-операций. Она меняется только при несовместимом изменении
snapshot/journal, security outbox или других сообщений. Параметра INI для её
подмены нет. Разные версии приложения с одним протоколом совместимы.
Одновременно поддерживается только один wire-формат; преобразователей и fallback нет.

## Проверка перед обменом

Каждый цикл начинается с небольшого `/replication/handshake`: TLS проверяет CA и имя/SAN в legacy_ca либо approved SPKI/mTLS
в pinned mode (0.5.0+); Bearer проверяет общий секрет, `X-Hemlock-Node` — ожидаемый node ID.
Название заголовка идентичности закреплено и не зависит от будущего имени продукта.
`X-Hemlock-Protocol` сообщает версию протокола, `X-Hemlock-App-Version` —
версию установленного приложения для диагностики. Handshake ограничен 16 KiB.

При совпадении сервер выдаёт случайное краткоживущее подтверждение обмена
(30 секунд, привязано к node ID, версии и процессу сервера). Оно передаётся
через `X-Hemlock-Exchange`. Сервер хранит не больше 64 подтверждений в RAM.
Status, snapshot, journal и security outbox требуют версию и действующее
подтверждение даже при прямом запросе в обход обычного polling.
Ответы также подтверждают версию и обмен; клиент проверяет их до применения
данных или acknowledgement. Перезапуск сервера требует нового handshake.

Нет версии/endpoint handshake — **Peer upgrade required**. Разные протоколы —
**Protocol version mismatch**. Dashboard показывает local/peer protocol и app
version, когда они известны. Эти ошибки красные; прежняя дата успешного обмена
не становится свежей. Ошибка авторизации и недоступность сети показываются
отдельно. Отсутствующий peer не считается синхронизированным.

## Что происходит во время паузы

Snapshot/journal/outbox не передаются и не принимаются; remote cursor/ack и
prune не применяются. Сохранённые правила, пользователи, protection и BGP
продолжают работать. Проверка протокола не меняет роль, не сбрасывает БД и
не запускает master-to-slave transition. Локальный security outbox продолжает
накапливаться, локальные уведомления работают по прежним настройкам.

Master retention при настроенном peer требует свежего успешного подтверждения
совместимости, в том числе между партиями удаления. Неподтверждённый или
несовместимый peer запрещает автоматический и ручной prune. На автономном
master без настроенного peer это условие не применяется.

Опрос периодически повторяет handshake. После совпадения протокола обмен
возобновляется автоматически: journal догоняется, а при смене истории или
недоступном cursor используется обычный согласованный snapshot. Security outbox
доставляется с существующей дедупликацией event ID, без повторного уведомления.
Журнал не сокращается; retention не удаляет старые копии аудита из journal,
backup или export и не гарантирует уменьшения размера файла SQLite.

## Короткий порядок обновления B → A

1. На обоих узлах проверьте роль, сохраните backup штатной CLI и отдельно
   INI/TLS/секрет. Не меняйте node ID, route owner или protection.
2. Если на старом релизе уже включён retention, заранее приостановите его
   и не выполняйте prune до обновления обоих узлов: старый код нельзя задним
   числом защитить новым handshake.
3. Обновите **slave B**, затем **master A** по фиксированному опубликованному
   тегу/commit согласно [LIFECYCLE.md](LIFECYCLE.md). Перезапускайте только Hemlock.
   GoBGP не перезапускается; сохранённые анонсы продолжают работать.
4. Между обновлениями возможна пауза репликации. Релизы без handshake
   несовместимы; старый интерфейс может показывать общую ошибку обмена.
   Никакой переустановки slave, init-db или удаления БД для обычного обновления нет.
5. После обновления A проверьте на обоих Dashboard свежий **In sync**, отсутствие
   ошибки версии, совпадение generation/history и догнавший cursor/zero lag.
   Проверьте доставку накопленного security outbox; zero lag правил сам по себе
   не доказывает его доставку. Проверьте BGP отдельно без изменения правил.
6. Только после проверки обоих узлов возвращайте ранее согласованный retention.
   Новых обязательных параметров INI нет; номер протокола не настраивается.

Первоначальная установка получает snapshot после успешного handshake.
Переустановка B из [PAIR_UPGRADE_040.md](PAIR_UPGRADE_040.md) — отдельный ранее
выбранный оператором сценарий смены размещения/путей, а не требование протокола.
Историческое переименование HTTP-заголовка было излишним разрывом совместимости;
переименование продукта само по себе не требует изменения протокола.

TLS model in 0.5.0 does not change protocol 3 or snapshot/journal/outbox formats. Public certificate introduction and local approval are separate from the authenticated protocol handshake; see [TLS_TRUST.md](TLS_TRUST.md).
