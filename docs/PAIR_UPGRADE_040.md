# Переход пары A/B на 0.4.0: A сохраняем, B устанавливаем заново

Это инструкция к **опубликованному поведению 0.4.0**, а не разрешение выполнять
работы. Master A остаётся источником правил/пользователей/аудита. Роль A не меняется,
автоматического failover нет. GoBGP на A не останавливать и не перезапускать:
во время остановки приложения он продолжает существующие маршруты.

## Что переносится на B

B устанавливается installer-скриптом на **чистую Debian 13**. Из прежнего B
переносятся только локальные настройки INI, его собственные TLS-файлы/публичный CA
и общий секрет репликации. Значения адаптируются к новым путям:

- `/opt/hemlock`, новый venv (не переносить старый);
- `/etc/hemlock/hemlock.ini`, TLS и token под `/etc/hemlock`;
- `/var/lib/hemlock/hemlock.sqlite`, новая пустая БД;
- пользователь/группа `hemlock`, unit `hemlock.service`, CLI `hemlock`.

Сохраните прежние node ID и уникальный route owner B, role=slave, peer identity
A, адреса/порты и согласованные route/protection/IRR параметры. Разрешите все
старые относительные пути относительно прежнего INI **до** адаптации; убедитесь,
что в новом INI, unit/drop-ins и executable shebang не осталось старых путей.
При HTTPS 443 отдельно перенесите смысл bind-capability настройки в новый unit.
Первый запуск B — announcements=no. Администратора на B не создавать.

**Не переносить на новый B:** старую БД, WAL/SHM, sessions, audit/security outbox,
replication cursor/history, старый venv или отдельный файл protection cache.
Правила, пользователи, принятые ASN-наборы и общий аудит получает штатная
репликация с A. Архив старого B можно оставить отдельно для отката, но не
восстанавливать в новую установку.

Накопленный protection A сохраняется вместе с его БД. Cache B создаётся заново
локальным IRR refresh, а не snapshot. Свежий ответ IRR **не гарантирует** полноту
исторического protection A. До разрешения B-анонсов сравните эффективные protected
сети обоих узлов. Исторические сети, нужные на B, согласуйте как явные
protected_prefixes в его локальном INI; этот INI входит в разрешённый перенос.
Проверьте успешную инициализацию каждого protected ASN. Если эквивалентность
защиты ещё не подтверждена, B остаётся announcements=no. Кэш не очищать ради
устранения ошибки и не считать, что он пришёл по репликации.

Installer отказывается при существующих путях/пользователях/GoBGP. Поэтому здесь
«B заново» означает чистую ОС/новую VM, а не удаление каталогов на действующем B
для обхода проверки. Сохранить **старый GoBGP B без перерыва** при переустановке
его ОС невозможно: это отдельное сетевое переключение оператора. Если требуется
переустановить только приложение на той же VM с работающим GoBGP, этот fresh
installer для такого сценария не подходит. GoBGP нового B настраивается отдельно,
реальные peers сначала disabled. Старый и новый B не работают одновременно с
одним IP/node ID. Работа GoBGP A от переустановки B не зависит.

## Короткий порядок

1. **Подготовка без переключения.** Выбрать один проверенный полный commit 0.4.0
   для A/B (тег 0.4.0 отдельно не создан). Определить реальные config/DB пути A из
   его сервиса. Сохранить приватные backups A и rollback-пакет/конфиг; подготовить
   B по INSTALL_B.md до старта сервисов: installer, новый venv, TLS/CA/secret,
   адаптированный INI, role=slave и announcements=no. Не переносить DB/cache.
2. **Перед окном.** На старой совместимой паре дождаться свежей синхронизации и
   отставания 0. Отдельно проверить подтверждение security outbox старого B:
   zero lag обычного журнала не доказывает отправку всех локальных auth событий.
   Неотправленные события должны дойти до A до отказа от старого B. На время
   переключения не менять правила/пользователей и не создавать тестовые входы.
3. **Вывести старое приложение B.** Остановить его фактический application unit,
   не оставлять его автозапуск рядом с новым B. Именно здесь начинается окно
   отсутствия синхронизации. Новую VM с тем же IP вводить только после исключения
   конфликта со старой. Не останавливать GoBGP A и не менять роли.
4. **Перенести A с данными.** На короткое время остановить только приложение A,
   создать окончательный SQLite backup штатным CLI. Выполнить A-only процедуру
   MIGRATION_LEGACY.md: новый код/venv/пользователь/пути, собственная БД A из
   закрытого backup, полный локальный protection, прежние node ID/owner/роль/TLS/
   секрет/peer параметры. Не выполнять init-db поверх A и не менять role на slave.
   Запустить только новое приложение A. Убедиться, что поколение/правила прежние,
   local RIB сохранена. Пока B не готов, статус соседа unavailable — ожидаемо.
5. **Запустить новый B.** После проверки INI/TLS создать его пустую БД через
   init-db, выставить владельца hemlock и запустить приложение по INSTALL_B.md.
   GoBGP нового B — отдельный первый запуск с согласованным конфигом/disabled
   peers; это не перезапуск GoBGP A. B должен получить согласованный snapshot A
   и догнать journal. Если B запущен до обновления A, ошибка peer authentication
   ожидаема: разные версии не синхронизируются. Не менять секрет/CA ради обхода.
6. **Проверить восстановление связи.** На обоих узлах версия 0.4.0+, роли A=master,
   B=slave, ожидаемые node IDs. Dashboard свежий In sync, отставание 0, совпадают
   history/generation и sequence/cursor; время последней успешной синхронизации
   обновляется несколько интервалов подряд. Проверить правила, пользователей,
   принятые ASN-наборы и общий аудит B; проверить ack новых auth outbox событий
   отдельно, когда они естественно появятся. Никаких фиктивных production events.
   Зафиксировать самостоятельную готовность protection B, а не только zero lag.

Синхронизация пропадает с остановки старого B и возвращается только после старта
совместимых A/B, завершения snapshot и догона journal. До этого зелёный статус
не ожидается. Остановка приложения A временно прерывает веб/изменения, **не BGP**.
Новые B-анонсы/рабочие peers включаются отдельным действием оператора после этих
проверок. При проблеме оставьте B-анонсы выключенными, A master/GoBGP работающими;
не восстанавливайте старую БД B поверх новой и не выбирайте второй master.

## Почему поменялся заголовок

В 0.4.0 заголовок identity peer был переименован при унификации продукта на
`X-Hemlock-Node`; обе стороны кода теперь используют только новое имя. Прежнее
wire-имя приведено в MIGRATION_LEGACY.md. Изменение было **избыточным разрывом
совместимости**: переименование продукта/каталогов само по себе не требует
менять wire protocol. Оно не добавило защиты, не связано с изменением SQLite/
journal/snapshot и не требовалось GoBGP. Правильным совместимым вариантом было
сохранить прежнее wire-имя либо предусмотреть явно проверенный переходный режим.

Этот документ не меняет код протокола и не обещает наличие такого режима в уже
опубликованном 0.4.0. Поэтому порядок выше учитывает реальную несовместимость,
не скрывает её под успешной синхронизацией и не предлагает ослаблять TLS/auth.
